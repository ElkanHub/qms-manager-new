# Security & Compliance Audit — QMS Manager (main @ 858fb15)

Date: 2026-09-04. Scope: the whole repository — 38 migrations (8.4k lines SQL), 36 SQL test files,
the Next.js app (~26k lines TS/TSX), CI, config, dependencies and the docs the build claims to follow.

## How this audit was done

- Six independent reviews, each reading the SQL and TS in full for one dimension: tenancy/RLS/audit
  substrate; document-control workflow guards; Next.js application security; identity, roles and
  governance; CI/config/dependencies/test harness; pluggable modules.
- The full migration chain and seed were applied from zero on a local Postgres 16 with a minimal
  Supabase shim (`auth.users`, `auth.uid()/jwt()`, the `anon`/`authenticated`/`service_role` roles and
  Supabase's default privileges). The SQL suite, typecheck, production build and `npm audit` were run.
- Every finding marked **[LIVE]** was reproduced by executing SQL against that schema. Findings marked
  **CONFIRMED** were traced end to end in code; **PLAUSIBLE** means a mitigation outside the repo
  (for example a hosted dashboard setting) could exist and must be checked manually.

## Headline

The foundation ideas are sound and several guards are genuinely strong (audit immutability, hash
chain, one-effective-version, invitation token mechanics, the human gate in training). But the system
is **not safe to expose to real tenants today**:

1. Because of how Supabase grants privileges, **every public RPC is executable by the anonymous role**.
   The migrations' `revoke ... from public` does not remove those grants. Combined with RPCs that never
   check `auth.uid()`, an unauthenticated caller can accept any invitation as any user id, claim the
   platform-owner seat if it is still empty, and bounce approvals back to draft. **[LIVE]**
2. Authorization in the document-control pipe is **role-only, never tenant-bound**, and several RPCs
   have **no authorization at all**. Any QA is QA of every tenant; any tenant admin can permanently ban
   the platform owner.
3. **MFA and deactivation are enforced only by page redirects** in Next.js, never by the database or by
   server actions.
4. Three switches that the spec says can never weaken a guard do weaken it: a caller-supplied training
   flag, an empty signing matrix, and a zero retention period.
5. **CI has never passed on `main`** (51 of 51 runs failed). The current failure is 8 SQL test files
   erroring before their assertions; `main` is unprotected; a shipped migration was edited in place.

Nothing in git history contains a secret. The audit chain, RLS reads, and break-glass gate held up
under scrutiny. The fixes for the critical items are mostly mechanical and are listed at the end.

## CRITICAL

### F-01 · Every `public.*` function is executable by `anon` and `authenticated`; the migrations' revokes are ineffective — [LIVE]

Supabase's platform init runs `alter default privileges in schema public grant all on functions to
postgres, anon, authenticated, service_role`. Every function the migrations create in `public` therefore
carries a direct EXECUTE grant for `anon`. The repo's pattern

```sql
revoke all on function public.accept_invitation(...) from public;
grant execute on function public.accept_invitation(...) to service_role;
```

(`supabase/migrations/20260101000300_phase3_identity.sql:261-262`, repeated for `bootstrap_platform_owner` at
`…000500_phase5_platform_governance.sql:423-424` and ~70 other functions) only removes the `PUBLIC`
pseudo-role entry. No migration ever revokes from `anon` or `authenticated`. On the built schema 139
SECURITY DEFINER functions in `public` are executable by `anon`; 10 of them never read `auth.uid()`/`auth.jwt()`:
`accept_invitation`, `bootstrap_platform_owner`, `save_signature_by_token`, `activate_scheduled`,
`start_retention_holds`, `verify_audit_chains`, `document_story`, `platform_actor_emails`, `verify_certificate`, `ai_usage_guard`.

Reproduced with `set local role anon` and no JWT claims:

- `accept_invitation(<token>, <attacker auth uid>, 'qa@a.test', …)` bound the attacker's identity to
  the tenant's **QA** invitation; `app.is_qa(attacker)` returned true. The email check compares
  against the caller-supplied `p_email`, so it binds nothing. Tokens are readable by every tenant user (F-14).
- `bootstrap_platform_owner(<attacker uid>, 'attacker@evil.test')` made the attacker the **platform owner**
  when no owner row existed yet (any environment before first owner sign-in, or with `PLATFORM_OWNER_EMAIL` unset).
- `request_changes(<approval id>, 'x')` moved a pending approval to `changes_requested` and the version back
  to `draft`; the audit row shows `actor_id = NULL`, `actor_email = 'System (automatic)'` (see F-02).

An attacker needs only the project URL and anon key (both shipped to every browser) plus, for the first
case, any `auth.users` id — which hosted Google sign-in mints for anyone because signups must be enabled
for the invite flow to work at all (F-16).

**Fix (one migration, then a convention):**

```sql
revoke execute on all functions in schema public from anon, authenticated, public;
alter default privileges for role postgres in schema public revoke execute on functions from anon, authenticated, public;
grant execute on function public.current_tenant_id(), public.is_platform() to anon, authenticated;
-- then re-grant each user-facing RPC to authenticated explicitly (the existing grant lines already do this)
```

Add `app.require_actor()` (`if auth.uid() is null then raise`) as the first line of every RPC, and a test that
iterates `pg_proc` for `public` functions with an `anon` ACL entry and fails if any exist beyond the two helpers.

### F-02 · Workflow RPCs with no authorization check at all — CONFIRMED, one path [LIVE]

Any authenticated user (and per F-01 any unauthenticated caller) can drive other people's documents:

| RPC | Location | Missing check |
|---|---|---|
| `submit_document(p_document)` | `20260201000600_dc_p6_new_sop.sql:69-99` | owner/role/tenant/document status |
| `request_changes(p_request, p_reason)` | `dc_p6:123-134` | any — bounces any pending approval to draft |
| `resubmit_document(p_document)` | `dc_p6:137-148` | any |
| `enter_effectiveness_review(p_cc)` | `20260201000700_dc_p7_change_pipe.sql:427-435` | any; also no elapsed-window check |
| `request_retirement(p_document, …)` | `20260201000800_dc_p8_retirement.sql:120-132` | any |
| `request_cc_clarification`, `reject_cc` | `dc_p7:179-192` | no state guard; rejecting leaves the document `locked_in_cc` forever |
| `waive_signature` | `dc_p7:341-353` | no state guard, no slot-exists check, no SoD (see F-05) |

`submit_document` by anon is stopped only by an accidental NOT NULL on `approval_requests.submitted_by`;
`request_changes` completes.

**Fix:** `submit_document`/`resubmit_document` require `d.owner_id = auth.uid() or app.is_qa(...)`, document
status in `('draft','in_review')`, and refuse a version referenced by `change_control_documents.target_version_id`
(see F-05). `request_changes` require HOD of the department at `hod_review` / QA at `qa_review`.
`enter_effectiveness_review` QA only. `request_retirement` owner/HOD/QA. Add state guards to the CC RPCs.

### F-03 · Authorization is tenant-blind: a QA in tenant B is QA in tenant A; an org admin can ban the platform owner — CONFIRMED

`app.has_role`/`app.is_qa` (`20260101000400_phase4_org_governance.sql:71-100`) read `user_roles` by user only.
Every DC-pipe RPC then checks the role and never compares the target row's `tenant_id` to
`current_tenant_id()`: `update_draft`, `reject_request`, `qa_approve`, `release_training`,
`begin_screening`, `classify_cc`, `approve_for_work`, `open_document_work`, `review_cc_document`,
`reconcile_cc`, `release_cc_training`, `close_cc`, `submit_impact`, `apply_signature` (v3),
`approve_retirement`, `withdraw_retirement`, `destroy_version`, `assign_training`, `complete_training`,
`issue_controlled_copy`, `reconcile_copy`, `conclude_periodic_review`, `dispatch_intake`, `create_change`
(targets never checked). The newer modules (training, copy register v3, SOP library v2, roles v2, flow map)
all do `x.tenant_id is distinct from public.current_tenant_id()` — the fix is to port that idiom.

Two worse cases have **no tenant and no plane check on a user id**:

- `public.org_deactivate_user(p_target_user, p_reason)` (`phase4:260-268`) → `app.deactivate_user`
  (`phase3:204-231`) sets `auth.users.banned_until = 'infinity'`. Platform actors' ids appear on the tenant
  audit chain (`switchboard.module_set`, `tenant.provisioned`), which every org user can read. An org admin
  can therefore ban the platform owner. No reactivation RPC exists anywhere, and `bootstrap_platform_owner`
  refuses while an owner row exists — the platform plane is dead.
- `public.revoke_role` (`phase4:160-190`; explicitly left as-is by `roles_three_axes.sql:293`) strips any
  role from any user in any tenant, including another tenant's last QA.

Exploitation needs a foreign UUID (random, not enumerable through RLS), so this is defence-in-depth for
documents but real for the user-id cases. The invariants doc promises the DB, not obscurity, enforces isolation.

**Fix:** `app.assert_same_tenant(p_row_tenant uuid)` used at the top of every RPC that takes a row id;
`deactivate_user`/`revoke_role` compare `actor_context(target).tenant_id` to the caller's and refuse
`plane = 'platform'` targets; add a reactivation RPC; add a sweep test that calls every `public` function with a
uuid argument as a tenant-B QA against a tenant-A row and expects failure.

### F-04 · MFA, deactivation and onboarding are enforced by page redirects only — CONFIRMED

- `src/lib/auth.ts:36-49`: `mfaRequired()` is true only when `nextLevel === 'aal2'`, i.e. after a verified
  TOTP factor exists. A new invitee who never visits `/mfa` is admitted with no second factor. No migration
  references `aal` at all, so a session at aal1 calls every RPC through PostgREST.
- Of 20 `"use server"` files only `pulse/actions.ts` and `documents/upload-actions.ts` call `requireOrgUser`.
  All other actions (including `applySignature` in `changes/actions.ts:108`, invites, deactivation, platform
  actions) go straight to `createClient().rpc(...)`. Route handlers under `(org)` (certificates, copy sheet,
  copies export) have no `requireUser`.
- `app.deactivate_user` flips `users.status` and bans the auth row but does not delete sessions/refresh
  tokens, clear `user_roles`, or strip `platform_role`/`tenant_id` from `app_metadata`. No RLS policy or RPC
  reads `users.status` (10 references in migrations, all roster helpers). A deactivated QA's access token
  keeps working until expiry; a deactivated platform admin keeps `is_platform()`.
- The "trusted device" feature (`MFA_TRUSTED_DEVICE_DAYS`, `remember_device`, `qms_device` cookie) is written
  but never read; `p_days` is client-controlled and unbounded; the cookie is neither `Secure` nor `HttpOnly`.

**Fix:** `app.require_aal2()` = `(auth.jwt()->>'aal') = 'aal2'` in every controlled RPC preamble; treat "no
verified factor" as MFA-required in `mfaRequired()`; call `requireUser*()` at the top of every exported action
and route handler; in `deactivate_user` delete `auth.sessions`/`auth.refresh_tokens`, delete `user_roles`,
strip claims; join `users.status = 'active'` in `has_role`; either implement or remove trusted devices.

### F-05 · Guards that a switch or a caller flag turns off (Law A.5 violations) — CONFIRMED

1. **Training gate is a caller boolean.** `qa_approve(p_request, p_training_required)` at
   `dc_p6:195`: `if p_training_required and (v_ans->>'required')::boolean and not (v_ans->>'threshold_met')::boolean`.
   QA passes `false` and the document goes effective regardless of assignments. Only `true` is tested (`tests/26:80`).
2. **Empty signing matrix + admin waiver ⇒ zero signatures.** `set_classification_matrix` accepts
   `p_roles = '{}'` (`roles_three_axes.sql:473-484`); `required_signatories` then seeds no slots
   (`dc_p7:118-125, 311-313`); `waive_signature` updates 0 rows and calls `check_cc_completion`, which sees no
   unsigned slot and advances to `pending_reconciliation`. An `org_admin` requester can also waive every slot on
   their own change (no `enforce_sod`).
3. **Retention period has no floor.** `set_retention_period(0)` (`dc_p8:57-67`) → `retention_until = now()`
   → `destroy_version` passes immediately.
4. **Change-control bypass through the new-SOP pipe.** `submit_document` takes the latest `draft` version of any
   document regardless of `documents.status` (`dc_p6:74-78`). After `approve_for_work` creates the CC target
   draft and locks the document, anyone submits that draft through the ordinary pipe; a second QA approves;
   `make_effective` supersedes the live SOP with **no classification, no signatures, no reconciliation**.
5. **`release_cc_training` has no threshold check** (`dc_p7:399-405`); `release_training` does.
6. **Training config is unvalidated platform JSON**: `threshold` 0 → always met; `assume_met` true feeds
   `qa_approve`; zero assignments count as met (`training_module.sql:1104-1131`).
7. **Legacy import** (`legacy_import.sql:30-31`, `dc_p4_numbering.sql:100-104`) is a permanent, `org_admin`-callable
   path to `status='effective'` with no approval, no signatures and no content, and exempt from number uniqueness.

**Fix:** drop `p_training_required` (decide from `is_training_required(version)` and make any override an
audited, reasoned QA action); matrix must be non-empty and contain `qa`; `waive_signature` requires
`status='signatures_pending'`, an existing slot, SoD, and never `qa`; `check (months >= 1)` on
`retention_settings` and compute from `superseded_at`; `submit_document` refuses CC-target versions and
`locked_in_cc` documents; port the threshold check into `release_cc_training`; constrain config values;
gate legacy import behind an audited, platform-set migration window and require QA.

### F-06 · The pre-deployment gate has never been green; `main` is unprotected — CONFIRMED

- All 51 CI runs on `main` (2026-07-01 → 2026-07-22) concluded `failure`. The latest
  (`actions/runs/29914884184`) fails 8 SQL files with `permission denied for table t`: tests create a temp
  table as `postgres` and then read it after `set local role authenticated`; Supabase's default privileges are
  schema-scoped and do not cover `pg_temp`. Files 05, 06, 07, 08, 21, 23, 25, 45 therefore **abort before
  their assertions** — platform governance, switchboard, the Phase 7 isolation sweep, onboarding, the read
  surface, library, intake and the roles refactor are unproven in CI. (They pass when the temp tables are
  readable, so the SQL under test is not itself broken.)
- 17 of 36 test files never `set role` at all (26–47); they exercise SECURITY DEFINER preambles via
  `request.jwt.claims` but no RLS policy introduced after Phase 7 is read-tested.
- 18 non-PR commits landed directly on `main`, including the ones introducing most DC migrations; there is no
  branch protection, CODEOWNERS, lint, TS test, or `npm audit` step.
- `supabase/migrations/20260301000100_training_module.sql` was rewritten after merge (`371cf35` → `21b2491`):
  new columns, new functions (`ai_usage_guard`, `ai_usage_summary`), changed signatures. A hosted DB that pushed
  between those commits will never receive them, contradicting README's "never edit a shipped one".
- `assert_raises` (`tests/_helpers.sql:13-21`) catches `when others`, so a typo passes as "guard fired".

**Fix:** in `scripts/run-sql-tests.mjs` after `begin`, run
`alter default privileges for role postgres grant select on tables to anon, authenticated;` (transactional,
rolled back with the file) or `grant select on t to authenticated` in each affected test; make
`assert_raises` take an expected message fragment; add negative cross-tenant read blocks under
`set local role authenticated` to files 26–47; protect `main` (PR + green `build-and-test` + review); move the
post-merge training edits into a new migration; add ESLint, a TS test runner, and `npm audit --audit-level=high` to CI.

## HIGH

**F-07 · Tenant-controlled `content_ref` reaches a service-role signer, a server `fetch`, and an iframe — CONFIRMED.**
`documents/actions.ts:15`, `intake/actions.ts:24` accept free text; the only DB check is a `.docx/.doc` suffix
regex (`review_annotation.sql:24-32`). `src/lib/content-ref.ts:77-85` signs any `storage:<path>` with the admin
client without checking the tenant prefix (no `storage.objects` policies exist). `src/lib/extract-docx.ts:113`
fetches any `https://` URL server-side (SSRF). `documents/[id]/Viewer.tsx:20-23` puts the ref into `iframe src`
verbatim when the renderer is `internal` — `javascript:alert(1)//.docx` passes the regex. With `ms_online` the
signed URL of a controlled document is handed to `view.officeapps.live.com` with no documented data-processing
decision. *Fix:* DB and action accept only `storage:<current_tenant_id>/…` refs registered in `stored_files`;
`resolveContentUrl` verifies the prefix; Viewer allows `https:` only; MS renderer opt-in and documented.

**F-08 · Open redirect in the OAuth callback — CONFIRMED.** `src/app/(auth)/auth/callback/route.ts:10,18`
redirects to `new URL(next, origin)`; `next=https://evil.example` or `//evil.example` leaves the site right after
Google SSO. *Fix:* accept only `/^\/(?!\/)/`.

**F-09 · Platform users read tenant documents without a break-glass gate (`NULL <> x`) — CONFIRMED, [LIVE] past the guard.**
`read_document` (`sop_library_v2.sql:300`, `dc_p2:133`): `if d.tenant_id <> public.current_tenant_id() then raise`.
For a platform user `current_tenant_id()` is NULL, the comparison is NULL, nothing raises. Reproduced: a platform
owner with `has_open_gate = false` got past the tenant guard (the call then failed only because the fixture had no
effective version). Same pattern in `toggle_favorite` (`dc_p3:37`), `dispute_intake:104`, `dispatch_intake:16`.
*Fix:* `is distinct from` everywhere, or raise when `current_tenant_id() is null`.

**F-10 · Electronic signature record is not Part 11-grade — CONFIRMED.** `signatures` stores signatory, time,
meaning and waived flag (`dc_p7:48-61`); no version id, no content hash, no re-authentication event.
`apply_signature` v3 (`signing_v2.sql:17-41`) requires only that a specimen image exists; `p_meaning` may be
empty. CC target revisions can be reviewed, signed and made effective with `content_ref` null (`update_draft`
refuses `locked_in_cc`, nothing else can set content). `reconcile_cc` attributes `version.effective` to the
requester instead of the QA (`dc_p7:418`). *Fix:* fresh AAL2 step-up at signing recorded on the row; store
`version_id` + `sha256(content)`; require non-empty meaning; refuse content-less approval; attribute to the caller.

**F-11 · `approve_for_work` lock check is a TOCTOU — PLAUSIBLE.** `dc_p7:254-273` reads other CCs' statuses
without a lock and sets `locked_in_cc` unconditionally; two concurrent approvals both create target revisions and
the second silently supersedes the first. *Fix:* `select … for update` on targets, then `update … where status='active'`, raise if not found.

**F-12 · Org lockout: the last QA can be removed and nothing can restore one — CONFIRMED.** Self-revoke via
`revoke_role`, moving self out of the QA department (`sync_qa_marker`), or an org admin deactivating every QA
(F-03). Afterwards every QA-granting path is QA-only and the platform has no RPC to re-seed a QA into an existing
tenant. *Fix:* refuse operations that leave zero active QA-marker holders; owner-scope "reseed QA invite" RPC.

**F-13 · Legacy `complete_training` bypasses the assessment — CONFIRMED.** `dc_p9_modules.sql:81-92` is still
granted to `authenticated`, never redefined by the training module, and lets a trainee mark a *package* assignment
completed with no attempt or certificate; `is_user_trained`/`version_training_met` count it. *Fix:* raise when
`a.package_id is not null`; add tenant check; delete `completeTraining` from `oversight/actions.ts`.

**F-14 · Invitation tokens are plaintext and readable by every tenant user; no revocation exists — CONFIRMED.**
`phase3:27, 81-89` (select policy + grant on `invitations` incl. `token`). Consumed by a GET render
(`invite/accept/page.tsx:168-171`), so a crafted link burns a victim's invite. Status enum has `revoked` but no RPC
sets it. Combined with F-01 this is the QA-takeover path. *Fix:* store `sha256(token)`; column-level revoke of
`token`; explicit POST accept; `revoke_invitation` RPC.

**F-15 · Every employee can read the whole tenant audit trail including PII; platform-email masking is app-side only — CONFIRMED.**
`audit_org_read` (`phase7:19-20`) is tenant-wide for all `authenticated`; `submit_onboarding` writes every answer
verbatim into `new_value` (`onboarding_v2.sql:293`); `actor_email` is always filled (`actor_storage.sql:60-65`) and
`status-strip.tsx:24` reads it unmasked. `platform_actor_emails` is an oracle for "is X a platform operator"
callable by any authenticated (and, per F-01, anon) caller. *Fix:* QA/org-admin policy plus a "my own actions"
policy; mask at write time; drop the oracle; stop writing raw onboarding answers.

**F-16 · Hosted auth must have signups ON for the invite flow to work — PLAUSIBLE.** `config.toml:20` says
`enable_signup=false`, but the app never pre-creates `auth.users`; the Google identity is minted at sign-in and only
then bound. So production necessarily allows any Google account to create an auth identity (dead-ended, but a valid
uid for F-01). *Fix:* `admin.auth.admin.createUser({email, email_confirm:true})` at invite time so signups can be off;
publish the hosted auth settings as a versioned checklist (Email provider off, redirect allow-list, JWT expiry, rotation).
